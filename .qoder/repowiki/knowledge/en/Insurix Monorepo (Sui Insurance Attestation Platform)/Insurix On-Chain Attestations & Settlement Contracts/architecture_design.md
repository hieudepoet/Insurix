Three layered Move packages under `contracts/`:

- `attestations/packages/attestations` — the core registry: a shared `Registry` singleton derives per-subject `Box` addresses via `derived_object::derive_address(BoxKey{subject, revoked})`. `Attestation<T>` is `key`-only (no `store`/`drop`), stored in either the active or revoked box address; status is determined by ownership, not a field. Authority is uniformly gated by `Permit<T>` minted only by `T`'s defining module, so the attester identity is the package's original publish address (`type_name::original_id<T>()`). Display registration is append-only via a parked `DisplayCap` on the Registry.
- `attestations/demo` and `attestations/examples` — concrete schemas (auditor_a/b/c, subject_example, dependency_example) that follow the same pattern: define a `has store` payload struct, mint an admin capability in `init`, expose `register_*_display`, `attest_*`, and `revoke_*` wrappers around the core API.
- `insurix-schemas` — production schemas (`identity.move`, `external_data.move`, `fraud.move`) sharing common types through `lib.move`; each mirrors the auditor example pattern with its own verifier/admin cap.
- `insurix-settlement` — business layer built on top of attestations: `claim.move` defines a shared `Claim` object with pending/settled/rejected states, `escrow.move` holds SUI in a `Balance<SUI>` tied to a claim, and `settlement.move` orchestrates `try_settle` / `reject_claim` gated by `SettlementAdminCap`. Verification of required attestations is off-chain; the contract trusts the admin cap holder and records attestation IDs in events for indexer traceability.

Dependency direction is strictly one-way: settlement → claims + escrow + events; insurix-schemas → attestations core; demo/example schemas → attestations core. No cross-dependencies between sibling schemas.
